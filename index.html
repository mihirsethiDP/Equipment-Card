Equipment Card & Plant Drill-down

One card component that describes any node in a water-treatment plant, reached by drilling down Plant → Unit process → Unit → Equipment. It carries identity, live sensor readings, the work filed against that node, and exactly one call to action for the most pressing thing. At equipment level the card composes itself from the equipment's type rather than being a different card per type.

Information architecture

Plant  (Kanpur STP)
└── Unit process        Preliminary, Primary, Secondary, Tertiary, Sludge Handling
    └── Unit            Screen chamber, Blower group IU-G3, Aeration basin 1, …
        └── Equipment   Blower BL-2, Tank EQ-1, DO probe DO-1, Fine screen FS-1, …
The core rule. Every issue, task and maintenance record is filed against exactly one node and rolls up to every ancestor. It is never duplicated and never re-parented. In the card, items filed at the node you are on appear under Filed here, items inherited from descendants under From below, each tagged with its owning level and name.

Before you build

These are design references written in HTML, not production code to copy. Recreate them in the target codebase's existing environment — its component library, routing, state management and i18n. Specifically do not port: the in-memory N node graph (replace with the real asset API), the L string tables (replace with the app's i18n layer), the inline style strings assembled in JS, or the state chips and "jump to" row in the prototype header — those are demo scaffolding for reviewing states. Delete them.
Fidelity is high for colours, type, spacing, copy, severity vocabulary, block order and interaction behaviour — recreate those faithfully. The equipment illustrations are low-fidelity placeholders: CSS boxes standing in for real OEM artwork. Keep the reading-tag overlay and part-label positions as the contract.
Two blocking questions are still open. The config model currently allows issue and trigger scoping at equipment only, while the design needs plant, unit-process, unit/group and equipment. And instrument and fixed are not in the locked archetype set AR-1…AR-7. Both need an ADR — see Known gaps in the README.
Note on the source prototypes. The .dc.html files fetch their runtime (React, ReactDOM, Babel) from unpkg at load time, so they need a network connection and take a moment to render. The standalone bundle above needs neither.
